# 市政采购公告档案

面向市政采购档案员的公告留存工具：输入公告号，从本地示范站采集招标公告正文与唯一附件，按站点修订号逐版留档。网站改稿、换附件、撤稿后，旧版仍可核对、下载。

技术栈：FastAPI + SQLite；Docker Compose 同时启动档案应用与可在浏览器改稿的本地示范站。

## 快速开始（Docker Compose）

```bash
docker compose up --build -d
```

- 示范站（可改稿/换附件/撤稿）：<http://localhost:8000>
- 档案采集应用：<http://localhost:8001>
- 健康检查：`curl -s http://localhost:8001/healthz`

首次启动示范站会写入两条示例公告（`ZFCG-2026-0001`、`ZFCG-2026-0002`）。在档案首页输入公告号即可采集。

停止并保留数据：`docker compose down`；同时删除数据卷：`docker compose down -v`。

## 使用流程

1. 打开档案首页，输入示范站上的公告号，点击“采集公告”。
2. 在示范站打开同一公告：
   - **改稿**：修改标题/正文并保存，站点修订号 +1；再次采集会新增存档版本。
   - **替换附件**：上传新附件，站点修订号 +1；再次采集会留存新附件，旧附件仍可下载。
   - **撤稿 / 恢复**：撤稿后站点对访客隐藏内容；再次采集只更新撤稿状态，不新建版本，历史版本仍可下载。
3. 档案公告页可查看版本历史、逐版正文与附件下载、采集/核对记录。
4. **差异核对与确认**：新修订采入后，最新版进入“待核”。打开差异核对页可按自然段查看与前一存档版的新增、删除、修改；附件指纹变化单独标明。档案员核对后提交确认，记录绑定两个版本与实际差异。

## 差异核对规则

正文按**自然段**（空行分隔的文本块）比对，匹配基于内容多重集计数，而不是位置：

- 完全相同的段落，即使在新版中**重复出现或调换位置**，也只计为“相同”，不会误报为新增/删除；
- 相同段落配对后剩余的段落，按字符相似度贪心配对为“修改”（段内以 `<ins>`/`<del>` 标出具体增删文字），配不上的分别计为纯新增、纯删除；
- 附件不并入正文段落，其 SHA-256 指纹、文件名、类型、大小变化在“附件指纹核对”卡片单独标明；
- 首个存档版本没有前一版可比对：正文段落全部列为新增，附件标注为首个版本。

核对确认的语义：

| 情况 | 行为 |
| --- | --- |
| 提交确认 | 记录写入 `review_confirmations`，绑定公告号、新旧修订号、两版正文/附件 SHA-256、完整差异快照与差异指纹（快照的 SHA-256） |
| 提交前又采入更新版本 | 事务内检测到最新修订号变化，**拒绝过期确认**（`StaleReviewError`），最新版保持待核；此前的确认记录仍可查阅 |
| 表单指纹与档案实际差异不一致 | 拒绝写入（`ReviewMismatchError`），提示重新打开核对页 |
| 同一修订重复确认 | 拒绝重复写入（`ReviewAlreadyConfirmedError`） |
| 确认写入失败（如磁盘错误） | 事务回滚，不产生核对记录，待核状态不变；原版正文与附件下载照常可用 |

确认写入与版本采集一样使用 `BEGIN IMMEDIATE … COMMIT` 单事务，并在同一事务内复查最新修订号与两版指纹，避免读与写之间落入新版本。确认后再次采入新版时，公告自动重新进入待核，历史确认逐版保留。

## 一致性规则

采集流程先读元数据、下载附件、再读一次元数据，并要求：

- 两次读到的修订号、正文、附件描述、撤稿状态完全一致（防止采集中途站点改稿）；
- 正文修订号与附件修订号相同；否则整次拒收；
- 附件实际字节长度与 SHA-256 与源站声明一致；否则整次拒收。

与档案比对时：

| 情况 | 行为 |
| --- | --- |
| 修订号更新 | 新增一个存档版本（正文 + 附件同事务写入） |
| 修订号相同、内容一致 | 不重复建版（`unchanged`） |
| 修订号相同、内容不同 | 报告源站冲突（`conflict`），不覆盖旧版 |
| 修订号回退 | 报告冲突，不创建、不覆盖 |
| 同号仅撤稿状态变化 | 更新公告级撤稿标记，不新建版本 |

**不可变与原子性**：版本行（正文、附件字节与指纹）一经写入不再修改；撤稿状态保存在公告级。每个版本的公告行、版本行、附件 BLOB、日志在同一 `BEGIN IMMEDIATE … COMMIT` 中写入，SQLite 开启 WAL + `synchronous=FULL`。写入失败会回滚；进程在提交前被杀死，重启后只会看到完整旧版或没有新版，不会出现半份版本。

## 测试

```bash
pip install -r requirements-dev.txt
python -m pytest -q
```

测试覆盖：

- 首次采集、同修订重复采集、改稿、换附件、撤稿/恢复；
- 正文/附件修订不一致整次拒收；
- 同号不同内容冲突且旧版不变；
- 源站修订号回退；
- 附件 SHA-256/长度不符拒收；
- 数据库写入失败回滚、无半份版本；
- 子进程在事务提交前硬退出（模拟进程中断）后重启无残留；
- 档案 Web 页面、下载、错误提示与健康检查；
- 自然段差异：新增/删除/修改分类、段内增删标注、重复段落与换位不误报、无关段落不误判为修改；
- 附件指纹变化单独标明、首个版本无前置比对；
- 差异快照往返与差异指纹稳定性；
- 核对确认绑定两版与实际差异、重复确认拒绝、指纹/前一版不符拒绝；
- 交错采集（确认 r1 → 采 r2 → 确认 r2 → 采 r3 重新待核）；
- 过期确认在新版采入后被拒、旧确认仍可查；
- 确认写入失败保持待核且正文/附件下载可用；
- 核对全流程 Web 页面（差异页、确认页、过期与重复提示、首页核对状态）。

## 源站 API（示范站）

- `GET /api/notices/{公告号}`：公告元数据（含修订号、唯一附件描述）
- `GET /api/notices/{公告号}/attachment?rev=N`：附件字节

档案应用通过 `SOURCE_BASE_URL` 指向该站。若接入其他站点，只需实现相同的元数据字段与附件校验语义。
